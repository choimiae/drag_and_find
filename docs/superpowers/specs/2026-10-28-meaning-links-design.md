# 뜻 모음 항목을 실제 연결 문서로 이어 주기 — 설계 문서

- 작성일: 2026-10-28
- 상태: 승인됨 (2026-10-28)
- 기반 문서: `docs/superpowers/specs/2026-10-24-disambiguation-design.md` (뜻 모음 기능의 원 설계. 이 문서는 그 §6.2의 "항목과 연결 문서 짝짓기" 규칙만 바꾼다)

## 1. 문제와 목적

카드의 "다른 뜻" 목록에서 눌러도 아무 일이 없는 줄이 있다. 원 설계는 뜻 모음 문서를 **글자만**(`prop=extracts`) 받아 와서, 줄이 연결 문서 제목으로 **시작하는지** 보고 눌릴 곳을 추측했다. "데이터베이스 트리거"처럼 문서 이름으로 시작하는 줄은 맞히지만, "마진(痲疹)은 홍역을 가리키는 의학 용어이다."처럼 문장으로 쓰인 줄은 못 맞힌다. 실제로 "마진"은 여섯 줄 모두 눌리지 않는다 (원 설계 §3 "제외"에 후속 과제로 적어 둔 항목).

목적: 위키백과 문서에 이미 들어 있는 연결(링크)을 그대로 읽어, 추측 없이 각 줄의 목적지를 안다. 문서가 없는 뜻만 글자로 남긴다.

## 2. 조사 결과 (2026-10-28, 실제 응답 관찰)

`action=parse&prop=text|links`로 받은 HTML을 고정 데이터의 아홉 단어(트리거·마진·포트·플랫폼·모델·버블·커널·터미널·스레드) 전부에서 확인했다.

- 항목은 전부 `<ul><li>…</li></ul>`이다. 소개 문장은 `<p>` 하나뿐이라 자연히 제외된다. `<dl>`·`<ol>`·각주·HTML 주석은 없었다(아홉 문서 기준)
- 묶음 제목은 `<div class="mw-heading mw-heading2"><h2 id="…">기본 의미</h2></div>` 형태. 오래된 문서는 `<h2><span id="…"></span>기본 용어</h2>`처럼 제목 안에 빈 `<span>`이 끼어 있다(모델·커널 등). 제목 글자는 안쪽 태그를 벗겨 읽어야 한다. `<h3>` 소제목도 있다(포트 "기술" 아래 "컴퓨터 과학")
- 항목 안에 하위 목록이 중첩되기도 한다(포트: "컴퓨터 하드웨어 포트" 아래 "마이크로컨트롤러 포트"). 지금의 글자 방식은 이것을 별도 줄로 평탄하게 받고 있다
- 각 줄의 **첫 번째 링크가 그 뜻의 문서**다. 마진의 "마진(摩震)은 후삼국 시대에 …" 줄은 맨 앞 "마진" 글자가 태봉으로 연결돼 있고, 이어지는 후삼국 시대·궁예·904년은 설명 속 링크다
- 링크 형식: 일반 `<a href="/wiki/%ED%83%9C%EB%B4%89" title="태봉">`, 넘겨주기 `class="mw-redirect"`, 다른 뜻 모음으로 가는 `class="mw-disambig"`(마진 → 여백), **없는 문서** `<a href="/w/index.php?title=…&redlink=1" class="new">`(마진 (1867년), 플랫폼 (소설), 플랫폼 (2006년 영화))
- 링크가 아예 없는 줄도 있다(트리거: "트리거(Trigger)는 네이버웹툰의 웹툰이다")
- 같은 응답의 `links`는 문서 안 모든 링크를 `{ns, title, exists}`로 준다. 없는 문서는 `exists: false`, 특수·파일·위키백과 이름공간은 `ns ≠ 0`
- 본문 끝의 동음이의 안내 상자(`<table class="dmbox">`)와 위키낱말사전 상자(`<div class="side-box">`)에는 `<li>`가 없다. 단 안전을 위해 `<table>` 안은 무시한다
- 실제 문서에는 각주 목록(`<ol class="references">`)과 항목 안 각주 번호(`<sup class="reference">`)가 흔하다(`insource:"<ref"` 검색으로 약 345개 동음이의 문서). 옛 글자 방식(TextExtracts)은 각주를 벗겨 줘서 보이지 않았다
- 배경 서비스 워커에는 `DOMParser`가 없다 (§6.3의 근거)

## 3. 범위

### 포함
- 뜻 모음 문서의 본문을 글자(`prop=extracts`) 대신 HTML(`action=parse&prop=text|links`)로 받는다
- 각 항목 줄의 **첫 번째 일반 문서 링크**를 그 항목의 목적지(`title`)로 삼는다. 없는 문서(빨간 링크)나 링크 없는 줄은 지금처럼 글자만 둔다
- 기본 뜻(`basic`)·같이 보기 제외·콜론 앞 이름표 등 나머지 해석 규칙은 글자 방식과 같은 결과가 나오게 HTML에서 다시 구현한다
- 테스트 고정 데이터를 HTML 응답으로 갈아 끼운다

### 제외 (바꾸지 않는 것)
- 자동 선택 후보(`candidates`)와 그것을 가져오는 요청(`generator=links` 첫 문단). 원 설계 §6.2가 후보 집합을 바꿨을 때 맞힘이 나빠진 기록이 있어, 이번에는 후보를 건드리지 않는다. 사전 시험 13문장의 기대값도 그대로다
- 기본 뜻 줄을 누를 수 있게 하기 (트리거 "총의 방아쇠" 줄 → 방아쇠). 지금처럼 글자만 보여 준다
- 빨간 링크 줄에서 뒤쪽 링크로 대신 이동하기 ("플랫폼 (소설)은 미셸 우엘벡의 소설이다" → 미셸 우엘벡). 뜻이 아닌 설명 속 문서로 보내면 오히려 헷갈린다
- 21개 넘는 연결 문서의 나머지 후보, 뜻 목록으로 돌아가기 버튼 (원 설계의 제외 항목 그대로)
- 카드 모양·설정·권한·연결 사이트. 모두 그대로다

### 성공 기준
- "마진"을 드래그 → "다른 뜻" 여섯 줄 중 다섯 줄이 파란 알약으로 눌리고, 독립운동가 줄만 회색 글자로 남는다. "마진(痲疹)은 홍역을 …" 줄을 누르면 홍역 요약으로 바뀐다
- "트리거"는 지금 눌리던 줄이 그대로 눌리고, "〈Trigger (EP)〉" 줄이 새로 눌린다
- 단위·E2E 테스트와 사전 시험 13문장 고정 테스트가 전부 통과한다

## 4. 화면

바뀌지 않는다. 파란 알약(누를 수 있음)과 회색 점선(글자만)의 모양·규칙은 그대로이고, 파란 알약이 되는 줄이 늘어날 뿐이다. 설정·스토어 문구·개인정보 문서도 손대지 않는다 (연결하는 사이트와 보내는 데이터가 같다).

## 5. 데이터 모양

`lib/lookup/types.ts`의 `Meaning`·`DisambiguationInfo`·`LookupResult`는 **그대로**다. 캐시 형식도 같다. 바뀌는 것은 `Meaning.title`을 채우는 방법뿐이다.

HTML 해석 함수가 안에서 쓰는 중간 모양 (외부로 나가지 않음):

```ts
/** parse 응답의 links 항목. */
interface ParsedLink {
  ns: number;
  title: string;
  exists: boolean;
}

/** 본문에서 꺼낸 항목 하나. */
interface ListItem {
  text: string;            // 태그를 벗기고 엔티티를 푼 글자 (하위 목록 제외)
  linkTitles: string[];    // 이 줄에 나온 /wiki/ 링크 제목들, 나온 순서
  section: string | null;  // 직전 묶음 제목 (없으면 null)
}
```

## 6. 동작

### 6.1 요청 (백그라운드, `WikipediaKoProvider.fetchDisambiguation`)

요약이 `type === 'disambiguation'`이면 지금처럼 2번을 **동시에** 요청한다. 1번만 바뀐다.

1. 본문 HTML + 링크 목록 (**바뀜**):
   `w/api.php?action=parse&page={제목}&prop=text|links&formatversion=2&disabletoc=1&disableeditsection=1&disablelimitreport=1&format=json`
   - 응답: `parse.text`(HTML 문자열), `parse.links[]`(`{ns, title, exists}`)
   - `page`는 요약이 돌려준 제목(넘겨주기가 이미 풀린 제목)을 쓴다
2. 연결 문서 첫 문단 (**그대로**): `generator=links&…&prop=extracts&exintro=1&…`

실패 처리는 원 설계 그대로다: 둘 중 하나라도 실패하면 `disambiguation` 없이 돌려주고 캐시에 넣지 않는다. `parse.text`가 문자열이 아니거나 `parse.links`가 배열이 아니면 실패로 본다.

### 6.2 HTML 해석 (순수 함수, `lib/lookup/disambiguation.ts`)

`parseDisambiguationHtml(html, links): { basic: string[]; meanings: Meaning[] }`

문서를 앞에서부터 한 번 훑으며 태그를 읽는다 (상태 기계. 스택 없이 상태 몇 개로 충분하다):

- **표 무시**: `<table>`을 만나면 짝이 되는 `</table>`까지 전부 건너뛴다 (동음이의 안내 상자)
- **각주 목록 무시**: `class`에 `references` 또는 `mw-references-wrap`이 든 `<ol>`·`<div>`도 짝이 되는 닫는 태그까지 건너뛴다 (제목 없는 각주 목록 대비. 각주 안 첫 링크는 뜻이 아니라 출처다)
- **각주 번호 제거**: 항목 글자를 읽기 전에 `<sup class="reference">…</sup>`를 안쪽까지 지운다 ("[1]"이 뜻 이름에 섞이지 않게)
- **묶음 제목**: `<h2>`·`<h3>`·`<h4>`의 안쪽 글자(태그 벗김)를 묶음 이름으로 삼는다
  - "같이 보기"·"각주"·"출처"·"참고 문헌"·"외부 링크"(글자가 정확히 같을 때)를 먼저 만나는 자리에서 **멈춘다** (이후는 모두 버림)
  - 이름에 "기본"이 들어간 **첫** 묶음이면 기본 뜻 묶음 켜기. 그 외 어떤 제목이든 기본 뜻 묶음 끄기 (글자 방식의 규칙과 같다)
- **항목**: `<li>`에서 항목을 열고, `<ul>`·`<ol>`·`</li>` 중 먼저 만나는 것에서 닫는다
  - 그래서 중첩 하위 목록은 부모 항목 글자에 섞이지 않고, 자기 `<li>`에서 별도 항목이 된다 (지금의 평탄한 줄 목록과 같은 결과)
  - 항목이 열린 동안의 글자를 모은다: 태그 벗김, HTML 엔티티 풀기(`&amp; &lt; &gt; &quot; &#39; &nbsp; &#160;`과 `&#NNN;`·`&#xHH;` 숫자형), 연속 공백은 공백 하나, 양끝 공백 제거
  - 항목이 열린 동안 만난 `<a>`의 `href`에서 문서 제목을 꺼내 순서대로 모은다:
    - `/wiki/…`이면 그 뒤를 `decodeURIComponent`하고 `_`를 공백으로, `#` 이후는 버림 (예: `/wiki/Trigger_(EP)` → `Trigger (EP)`)
    - `redlink=1`이 들어 있으면 쿼리의 `title`을 같은 방식으로 (예: `마진 (1867년)`)
    - 그 외(`#cite_note`, 바깥 주소, 위키낱말사전 `extiw` 등)는 모으지 않는다
  - 글자가 빈 항목은 버린다
- 닫힌 항목을 기본 뜻 묶음이면 `basic`에 글자만, 아니면 `meanings`에 넣는다

항목의 목적지 정하기 (`meanings`만):

- `linkTitles`를 앞에서부터 보며 `links`에서 같은 제목을 찾는다
  - `ns !== 0`이면(특수·파일·위키백과 이름공간) 건너뛰고 다음 링크를 본다
  - `ns === 0`인 **첫** 링크가 목적지다. `exists`이면 `title`에 그 제목, 아니면(빨간 링크) `null` — 뒤쪽 링크로 넘어가지 않는다
  - `links`에 없는 제목은 건너뛴다 (안전장치)
- 맞는 링크가 하나도 없으면 `null`
- `label` = 글자의 `:` 앞부분이 있으면 그것, 없으면 글자 전체 (지금 `labelOf` 그대로). 카드 쪽 40자 자르기·8개 초과 처리도 그대로

지금의 `parseDisambiguationText`·`buildMeanings`·"가장 긴 시작 제목" 규칙은 지운다 (이 변경으로 쓰이지 않게 되는 코드). 기존 `linkedTitles` 계산(연결 문서 응답에서 넘겨주기·없는 문서 가려내기)도 함께 지운다. `candidates` 계산은 그대로 둔다.

### 6.3 왜 손으로 HTML을 읽나 (설계자 판단)

- 배경 서비스 워커(MV3)에는 `DOMParser`가 없다
- 대안들을 보류한 이유:
  - 페이지 쪽(콘텐츠 스크립트)에서 DOM으로 해석: 조회·캐시가 백그라운드에 있어 HTML을 페이지로 보냈다 다시 받아야 하고, 구조가 두 곳으로 갈라진다
  - `offscreen` 문서: 권한이 하나 늘어 스토어 심사 범위가 넓어진다
  - HTML 해석 라이브러리: 새 의존성. 필요한 것은 `li`·제목·`a`의 `href`뿐이라 과하다
- 위키백과가 돌려주는 HTML은 기계가 만든 정형 구조라, 위 상태 기계로 충분하다. 한계는 §9에 적는다

### 6.4 다른 뜻 누르기

원 설계 §6.4 그대로. `title`로 요약을 찾으므로 넘겨주기(`mw-redirect`) 제목은 요약 쪽에서 풀리고, 다른 뜻 모음(`mw-disambig`, 예: 여백)으로 가면 그 문서의 뜻 목록 카드가 뜬다.

## 7. 요청 수와 성능

- 뜻 모음 단어: 요청 3번(요약 1 + 추가 2, 동시). **지금과 같다**
- parse 응답은 글자 응답보다 크다 (관찰: 4~6KB, 글자 응답은 1~2KB). 뜻 모음 단어에만 해당하고 결과는 캐시되므로 체감 차이는 없다
- 해석은 한 번 훑기(문서 길이에 비례)라 수십 KB여도 1ms 안팎이다

## 8. 시험

### 단위
- `parseDisambiguationHtml` — 실제 응답 고정 데이터로:
  - 마진: `meanings` 6개, 앞 5개 `title`이 태봉·홍역·한계·중간 이윤·여백, 마지막(독립운동가) `null`
  - 플랫폼: "플랫폼 (소설)" 줄은 `null` (빨간 링크 뒤의 미셸 우엘벡으로 가지 않음), "승강장은 …" 줄은 `승강장`
  - 트리거: `basic` 2개(글자만), "〈Trigger (EP)〉" 줄은 `Trigger (EP)`, 웹툰 줄은 `null`, "같이 보기" 이후 없음, 안내 상자 글자 없음
  - 포트: 중첩 하위 목록("마이크로컨트롤러 포트")이 별도 항목으로 평탄하게 들어가고 부모 항목 글자에 섞이지 않음
  - 모델: 제목 안에 빈 `<span>`이 있어도 "기본 용어" 묶음이 `basic`으로 들어감
  - 손으로 만든 짧은 HTML로: `<h3>` 소제목이 기본 뜻 묶음을 끄는지(고정 데이터에는 "기본" 묶음 아래 `<h3>`가 있는 문서가 없다), 엔티티 풀기(`&amp;`·`&#160;`), `<table>` 안 `<li>` 무시, `#cite_note`·바깥 링크 건너뛰기, `ns !== 0` 링크 건너뛰기, `links`에 없는 제목 건너뛰기, 빈 글자 항목 버림, 빈 문자열 입력
  - 나머지 고정 데이터 5개(모델·버블·커널·터미널·스레드)는 `meanings`의 `title`이 하나 이상 채워지는지와 `null`이 아닌 `title`이 모두 `links`에 있는지만 확인한다 (회귀 감시)
- 제공자(`wikipedia.test.ts`): 뜻 모음일 때 요청 3번이고 그중 하나가 `action=parse`인지, parse 응답이 모양에 맞지 않을 때(`text` 없음·`links` 배열 아님) `disambiguation` 없음, 추가 요청 실패 시 기존 결과 — 기존 사례들을 parse 고정 데이터로 옮긴다
- `pickSense` 사전 시험 13문장: **기대값 변경 없음** (후보가 그대로이므로). 바뀌면 설계 위반이다

## 9. 알려진 한계 (설계자 판단)

- `<li>`가 아닌 형태(문단 `<p>`)로 적힌 뜻은 항목이 되지 않는다. 글자 방식은 모든 줄을 항목으로 삼았으므로 이 점은 달라진다. 위키백과 동음이의 문서 지침이 글머리 기호 목록을 요구하므로 실제로는 드물다
- 표 바깥에 틀(템플릿)이 만든 `<li>`가 있으면 항목으로 섞일 수 있다. 각주 목록은 위 규칙으로 걸러 처리한다
- 하위 목록 뒤에 이어지는 부모 항목의 꼬리 글자(`<li>A<ul>…</ul>꼬리</li>`)는 버려진다
- 줄의 첫 링크가 뜻이 아닌 설명 속 문서인 경우(지침을 어긴 줄)는 그 문서로 간다. 관찰한 아홉 문서 중 하나 있다: 터미널의 "버스의 터미널은 버스 터미널이다" 줄은 첫 링크가 "버스"라 버스 문서로 간다. 지금 글자 방식도 줄 머리 "버스"로 짝지어 같은 곳으로 가므로 나빠지는 것은 아니다. 굵은 글자 링크를 우선하는 식의 보정은 이번 범위 밖이다
